# 02 · 归档格式与换锁

## `.patch_N` 归档布局（小端）

```
偏移 0   72 字节头      <III20sQQ24s
            magic = 0xF0000011,  unk = 1,  count = 资源数,
            total = 整个文件大小, 其余保留 0
偏移 72  每个资源类型 32 字节  <IIQIIII
            0, 0, TYPE(=0xA14E8DFA2CD117E2 = "lua"), count, 0, 16, 16
偏移 104 每个资源项 80 字节  <7Q6I
            name_hash(资源路径的 MurmurHash64A), TYPE, offset, 0,0,0,0,
            length, 0, 0, 16, 16, index
数据     每段正文 16 字节对齐： u32 body_len, u32 version(=2), body[…], 补齐
```

- 一个归档可以放**多个 addon**（`count>1`，按 `index` 顺序）；loader 逐个读 `-- HD2-Addon:` 头。
- 工程里常见三种形态：裸 `patch_N` 文件、Arsenal zip（`Addon/9ba626afa44a3aa3.patch_0`）、目录（`data/9ba626afa44a3aa3.patch_0`）。工具三种都认。

## 🔴 铁律：换锁必须保留原 `name_hash`

`name_hash` 是**资源路径**（addon 名之类）的 MurmurHash64A，**不是**可以随手重算的东西：

```python
# ✅ 正确：拿解析出来的原 name_hash，只换正文
pairs = [(e['name'], H.envelope(new_body)) for e in H.parse(raw)['entries']]
out = H.make_archive_raw(pairs)

# ❌ 错误：按 addon 名重新算哈希
out = H.make_archive({'mods/starm/my_mod': H.envelope(new_body)})
```

用错法的后果不是报错，而是**静默**：loader 直接发现不了这些 addon。
特征现象：`BingusSharedLoader.log` 里 `Discovery: N declared entries` 的 N 突然只剩几个（没被改过的那些），
你自己那些 addon 一条 `loaded` 都没有。**修法**：从改之前的备份重做，用 `make_archive_raw` 带原哈希。

每次写完都断言一遍：

```python
assert [e['name'] for e in H.parse(out)['entries']] == [e['name'] for e in H.parse(raw)['entries']]
```

## 等长替换 vs 重建

- 锁值都是等长字符串：SHA-256 = 64 字符、构建号一般 8 位数字。
  只在**原位置**换字符 → 归档偏移全不变 → 最安全（即"逐字节只差几个字节"，可用二进制 diff 验证）。
- 如果新构建号位数不同、或你还要改别的长度，就必须**重建归档**（`make_archive_raw`），
  重建后回读校验资源数、name 哈希、正文长度。
- 有的大 mod 会在正文里放绝对偏移/自校验长度，改长度有风险 —— 能等长就等长。

## 工具速用

```bash
python tools/hd2update.py inspect MyMod.zip     # 看资源名哈希、addon 名、当前锁、构建号
python tools/hd2update.py lock MyMod.zip --game-dir "<HD2>" --apply
python tools/hd2update.py verify MyMod.zip      # 退出码非 0 = 还有旧锁
```
