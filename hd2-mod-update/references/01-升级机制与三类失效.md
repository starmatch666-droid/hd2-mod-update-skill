# 01 · 升级机制与三类失效

## 构建锁长什么样

| 形态 | 例子 | 说明 |
|---|---|---|
| 文本锁（绝大多数） | `local SPEC={module_sha256="73374bd4…", owner_rva=54973760, …}` | 有的写 `game_dll_sha256`/`dll_sha256`；构建号常和它一起出现（`build=25327279`） |
| bytecode 锁 | 打包好的实现里两枚**大写** 64 位十六进制串（一枚 = game.dll，一枚 = helldivers2.exe） | 这种 mod 的实现是字节码，不好改，通常只能原位替换这两枚串 |

锁的行为：**运行时第一步就是校验 game.dll 的 SHA-256**；不符 → `unsupported_game_dll_no_write` → 直接退出，什么都不写。

## 为什么"只刷锁"通常就够

除了锁，addon 还会在运行时**自己校验**：

- `owner_rva`：从 game.dll 的某个固定偏移取一个指针（指向组件指针槽）；取出后按 `candidate_slot` 偏移找到表；
- 表映射：把整张 `hashmap` 逐字节比对；
- 行模板：把目标行（或锚行 + 邻域指纹）逐字节比对；
- 写入：预期值 → 写入 → 回读，三步都通过才算成功。

所以锁过期只会让 addon 不写；锁刷新后，如果 RVA/模板也变了，addon 会在日志里明确写
`not_found` / `template_mismatch` 之类，然后**继续不写**——不会误写。这就是为什么批量刷锁是安全的第一刀。

## 三类失效一览

| 类 | 现象 | 根因 | 修法 |
|---|---|---|---|
| A 构建锁 | 全addon静默失效，日志一条 `unsupported_game_dll_no_write` | game.dll 变了 | 离线刷锁（本 skill 主路径） |
| B 指针槽位 | 只有部分 addon 失败：`not_found`/`anchor_mismatch` | game.dll 编译变化 → 指针槽 RVA 变 | 只读探针取新 RVA → 重写 `owner_rva`/`candidate_slot` |
| C 表模板 | `template_mismatch`/`ldld_block_not_found` | 数据文件变化 → 记录序号/映射/行字节变 | 探针 dump 当前表 → 重算 `record_index`/`hashmap`/行 hex |

经验：**A 类 100% 会出现；B 类多半会出现（我们那次 RVA 从 41349312 变成 54973760）；C 类取决于改了多少数据。**

## 别忘了「同一个模组的多个保留版本」

作者经常**故意**保留同一个模组的多个版本（效果不同：比如 换弹减半 / 换弹减半+弹药翻倍；
过载不爆炸 / 再过载不爆炸+4发弹容 / 再加十倍镜）。这些是**彼此独立的制品**，
只刷当前在跑的那一个 = 其它的等你哪天切过去就静默失效（锁过期 → `unsupported_game_dll_no_write`）。

```bash
# 一次扫描（只读）：列出每个 zip 的 addon / 旧锁数 / 旧 build 号
python tools/hd2update.py variants "D:/Mods/MyMod-变体目录" --dry-run

# 一次刷新（备份 + 逐个体内回读校验）
python tools/hd2update.py variants "D:/Mods/MyMod-变体目录" --backup backup-variants
```

目录参数会自动取其下 `*.zip`，并跳过 `backup*/revision-backups/docs-*/requested-*/publish*`。
真实案例：一轮更新里有 14 个训斥/纪元变体 + 18 个其它模组的保留版本在等锁，
其中两个落后**两个**构建（还是上上版的 build 号）——它们从没被刷过。
